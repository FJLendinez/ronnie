# Migrations

Migrations are **versioned Python files** that store every schema change your
project makes, and a database table (`ronnie_migration`) records exactly
which ones have been applied. Nothing is implicit — you review the file,
commit it, and `ronnie migrate` applies it.

## The workflow

```bash
ronnie makemigrations      # detect model changes → write migration files
ronnie migrate             # apply pending (recorded in ronnie_migration)
ronnie showmigrations      # [X] applied / [ ] pending, per app
ronnie sqlmigrate blog 0002   # print the SQL before running it
```

A fresh project:

```bash
ronnie startproject mysite
cd mysite && ronnie startapp blog
# … declare your tables in apps/blog/models.py …
ronnie makemigrations
# Migrations for 'blog':
#   apps/blog/migrations/0001_initial.py
#     - Create table post
ronnie migrate
#   Applying blog.0001_initial... OK
ronnie showmigrations
# blog
#   [X] 0001_initial
```

## What a migration file looks like

```python
# apps/blog/migrations/0002_add_published_at.py
from ronnie.migrations import AddField, MigrationBase

class Migration(MigrationBase):
    dependencies = [("blog", "0001_initial")]

    operations = [
        AddField(table="post", name="published_at",
                 pytype="datetime.date", default=None),
    ]
```

- **`dependencies`** — must run after these migrations (auto-chained within
  an app; hand-set for cross-app).
- **`operations`** — the schema changes, in order.

## Operations

| Operation | Forward SQL | Reverse |
|---|---|---|
| `CreateTable(name, pk, fields)` | `CREATE TABLE` | `DROP TABLE` |
| `DeleteTable(name)` | `DROP TABLE` | `CREATE TABLE` (from state) |
| `AddField(table, name, pytype, default)` | `ALTER TABLE … ADD COLUMN` | `ALTER TABLE … DROP COLUMN` |
| `RemoveField(table, name)` | `ALTER TABLE … DROP COLUMN` | `ADD COLUMN` (from state) |
| `RenameField(table, old_name, new_name)` | `ALTER TABLE … RENAME COLUMN` | `RENAME COLUMN` back |
| `AlterField(table, name, pytype, default)` | table rebuild | rebuild back |
| `RunPython(fn, reverse_code=)` | calls `fn(db)` | calls `reverse_code(db)` |
| `RunSQL(sql, reverse_sql=)` | executes `sql` | executes `reverse_sql` |

`RunPython` / `RunSQL` are **hand-written only** (never autogenerated) —
data migrations and anything SQL-specific.

## The history table

Every applied migration gets a row:

```sql
SELECT app, name, applied_at FROM ronnie_migration;
-- auth     | 0001_initial | 2026-09-20T09:47:16
-- blog     | 0001_initial | 2026-09-20T10:12:44
-- blog     | 0002_add_... | 2026-09-20T10:13:02
```

This is the source of truth: `migrate` consults it, `showmigrations`
renders it, and `--fake` / `--fake-initial` write to it without executing
SQL.

## Rolling back

```bash
ronnie migrate blog zero     # roll back ALL blog migrations (reverse order)
ronnie migrate blog 0001     # roll forward/backward to a specific one
```

Only **reversible** operations can be rolled back — a `RunPython` without
`reverse_code` or a `RunSQL` without `reverse_sql` aborts the rollback with
a clear error telling you which operation is irreversible.

## Autodetection rules

`makemigrations` diffs your `models.py` (`TABLES` declarations) against the
accumulated state of existing migration files:

- New table in `TABLES` → `CreateTable`
- Table removed from `TABLES` → `DeleteTable`
- Field added → `AddField`
- Field removed → `RemoveField`
- Field type changed (e.g. `int` → `str`) → `AlterField` (sqlite rebuild,
  data preserved)

Use `ronnie makemigrations --check` in CI to fail when someone edited
models without committing a migration.

## Safety flags

```bash
ronnie migrate --dry-run          # print SQL, execute nothing
ronnie migrate --fake             # record without running (baseline adoption)
ronnie migrate --fake-initial     # initial tables already exist (adopt them)
ronnie makemigrations --dry-run   # show what would be generated
ronnie makemigrations --empty     # empty migration (hand-write operations)
ronnie makemigrations --name custom_suffix
```

## Framework apps ship their own migrations

`ronnie.contrib.auth`, `ronnie.contrib.sessions` and
`ronnie.contrib.redirects` include `0001_initial.py` — installing them and
running `ronnie migrate` creates their tables through the same system.
Your apps never share migration state with theirs.

## Transactional guarantee

Each migration runs inside one transaction — all operations or none — and
the WAL is checkpointed after every commit so external readers (other
processes, DB browsers) immediately see the result.
